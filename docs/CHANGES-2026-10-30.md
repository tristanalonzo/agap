## 2. What each one does

### #18 — PAGASA timestamp and area parsing (`backend/app/services/pagasa.py`)

`Issued at: 2:00PM, 21 October 2026` — no space before `PM` — used to match the regex but then
blow up in `strptime`, so `issued_at` came back `None` and the card showed no "Issued …" line.
The time and the AM/PM are now separate capture groups and get joined with a space.

`find_level_areas()` also split the affected-area text on `". "`, so a sentence with no space
after the period got glued onto the area name. It now splits on `"."`.

> Known limit, written in the review: this also cuts at abbreviations, so
> `"Metro Manila, Sta. Cruz and Rizal"` becomes `"Metro Manila, Sta"`. The old code had the same
> problem, so this is not a regression, but don't be surprised by it.

### #19 — Stale status (`frontend/src/App.jsx`)

This was the most serious one. After 5 minutes without a successful refresh, `markStale()`
overwrote the rainfall status to `"stale"` **no matter what it was**. If PAGASA had never loaded
at all, the card switched from UNAVAILABLE to STALE and said *"Showing the last result we got;
it may be outdated"* — about a result that never existed. That is exactly what safety rule 2
forbids.

Now only `fresh` → `stale` and `live` → `stale`. `unavailable`, `parse_error` and `demo` are left
alone. The cyclone card goes stale the same way, and the mode bar was updated to match.

### #20 — Demo replay chips (`frontend/src/data/demoReplay.js`)

The replay chips spread the live assessment and only overwrote some fields, so a live PAGASA
`issued_at`, `confidence` and `model_version` stayed on the 2020 storm cards. Those are cleared
now, `affected_area` says `"Quezon City (mockup example)"`, and `category_code` is set from the
scenario (`TS` / `TY` / `STY`) instead of being `null`.

### #21 — Location inputs (`LocationControls.jsx`, `App.jsx`)

`Number("   ")` is `0`, so typing only spaces passed the old empty check and sent `(0, 0)` to the
backend. Inputs are trimmed before both the parse and the check.

Two more: the manual lat/lon boxes now update when you press **Use my location**, and when a
point is rejected (outside QC, HTTP 422) the control says the cards below still show the previous
point instead of claiming the new one is live.

**Kurt — this changes a prop.** `LocationControls` now takes `assessedLocation` as well:

```jsx
<LocationControls location={location} assessedLocation={data.location} onChange={setLocation} />
```

### #22 — Civil defense states (`frontend/src/data/safety.js`, `index.css`)

`civilDefense` had no `none` entry, so when PAGASA was up and reported no warning, the Action /
SOS tab fell through to `unknown` and showed **"NO ORDER LOADED" / "No official evacuation order
loaded"** next to a green LIVE badge — reading as a failure when nothing had failed. There is now
a `none` state: "NO ACTIVE ORDER" / "No heavy rainfall warning in effect".

Red alerts were also styled yellow (`.banner.red` was `#fef3c7`). They are red now.

The `(TODO: confirm)` markers came out of the orange and yellow timelines — see section 5.

### #23 — Debris tab (`backend/app/api/debris.py`, `DebrisTab.jsx`, `client.js`, `safety.js`)

The biggest change of the batch, and the only new endpoint:

```
GET /api/v1/debris-matrix   →   backend/app/static/debris_matrix.json
```

The Debris tab used to show three hard-coded hazard rows copied from the design mockup,
regardless of category. It now fetches the real matrix and shows the vulnerabilities and
protective actions for the **current cyclone category** (TD / TS / STS / TY / STY), with the wind
band and relative threat level. The mockup array `debrisHazards` was deleted from `safety.js`.

It caches the matrix in `localStorage` under `agap.debrisMatrix` and shows STALE from that cache
when the backend is unreachable, the same pattern as the hotlines list. When the category is
`unknown` it says so and tells the user not to assume safe conditions, rather than showing
nothing or guessing a tier.

One review fix was pushed to that branch before merge (`1d6e8c8`): the card badged itself LIVE
whenever the reference matrix loaded, even though every row on screen is chosen by the cyclone
category — which is still the mock one. It now badges DEMO while the category is demo, per
safety rules 1 and 6.

## 4. A practical note on `docs/PROGRESS.md`

Every one of these PRs appended a line to the Log at the end of `PROGRESS.md`. That meant that
the moment the first one merged, **all the others conflicted** — on that one file, every time,
five times over. The code never conflicted once.

If several of us have PRs open at the same time, expect this. The fix is always the same: keep
both lines, oldest first, since the Log is newest-at-the-bottom.
